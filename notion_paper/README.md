## 十頁內容

1. 標註更新與評估計畫：今天的兩件事。
2. 如何用 11 張獨立圖片，讓 Gemma 產生資料卡。
3. 真實椅子範例：13 個欄位，以及估計值的界線。
4. 格式與數值檢查、總共最多三次作答，以及與論文的標註差異。
5. 標註進度、計算依據與預估完成時間。
6. 用真實家具需求比較三種模型；有參考輸入才安排對應模態。
7. 一道需求可有多個合適答案；用明示教學例說明 Hit 與真正 Recall。
8. 新主評估與論文／舊同資產診斷的差異，包含 P-only baseline 的候選構成。
9. ULIP-2 描述可作草稿；先人工審完每個可見條件的全候選正解，再封存與排名。
10. 標註結束後的六步流程，包含模型準備、需求撰寫與人工審核。

## 進度快照與科學界線

進度固定於 **2026-09-08 04:12:30（台北）**：本輪排程 46,004 件，已處理 25,089 件（54.54%），其中成功 25,063 件、失敗隔離 26 件，剩餘 20,915 件。起跑前另有 8 件成功，未算進本輪排程。

若持續運作且速度相近，預估 **9/9 上午**完成本輪標註，規劃時間窗 **09:00–12:00**。這是推估，非統計信賴區間；不含編碼、訓練、評估與排除整理。[原始進度證據](source/annotation_progress_snapshot.json) 留在交付資料夾，方便報告時交代時間基準。

標註保留論文的 11 視角與 Figure 2 欄位結構；目前模型為 Gemma 4 12B／BF16，論文使用 GPT-4o。提示、相機與重試為本地設定。尺寸、重量是模型估計，體積由估計尺寸相乘，不是實測。簡報使用的三張椅子圖是同一真實資產的原始渲染檔，沒有生成或改造紀錄照片；實際模型輸入為 11 張獨立圖片，透明背景合成黑底。

主評估改為[家具需求與多個可接受答案](../docs/INTENT_RETRIEVAL_EVALUATION.md)：query ID 獨立於資產 UID，每個可見模態條件各有覆蓋固定候選池的人工正解。主要報 Hit@1／Hit@5，輔助報真正 Recall；不冒稱與論文 R@k 完整等價。七模態只在原始參考輸入足夠時安排；舊兩觀測 × 三方法 × 七模態的 [42 組 same-UID 流程](../docs/CUSTOM_TABLE1_EVALUATION.md) 保留為診斷，不是新主評估。

CLIP 凍結與選模／評估重疊仍須揭露。Stage 2-off 沿用 Stage 1 候選向量，不輸入場景資訊；場景資訊開啟／關閉另作診斷。真實需求、逐條件人工正解仍待建立，正式評估尚未執行；第 7 頁數字是明示教學假設。G3 資料預檢與新主評估尚未接入現有自動鏈，不能把後續六步說成全部已自動接好。

## 製作與檢查

使用既有 MetaFind Python 環境的 `python-pptx 1.0.2` 與 Noto Sans CJK TC。以下命令只重建 PPT 和講稿，不會啟動標註、訓練或評估，也不會更新 Notion：

```bash
/home/kyzen/miniconda3/envs/MetaFind/bin/python notion_paper/source/build_deck.py
```

編輯成品前請自行保留版本，因為重建會覆寫 PPT 與講稿。PDF 與總覽是另外由實際 PPT 轉出，不能只改 JSON 就視為同步更新。

交付需核對 10 張投影片、10 份完整備忘稿、講稿文字一致、PPTX 結構、實際 LibreOffice PDF 渲染，以及逐頁文字與版面；不以只改 JSON 代替成品檢查。具體驗證範圍與結果見 [validation.json](source/validation.json)，全部交付檔案的 SHA 見 [delivery_manifest.json](source/delivery_manifest.json)；未以 Microsoft PowerPoint 桌面程式開啟。
